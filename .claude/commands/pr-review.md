PR のコード差分をレビューし、問題があればコメントして変更依頼、問題なければマージする。

## 前提

- 引数（$ARGUMENTS）にPR番号を指定する。例: `/pr-review 170`
- `gh` CLI が使用可能であること
- **マージ権限について**: CLAUDE.md の「マージは原則AIが行わず、ユーザーが確認してからマージする」の**例外を、このスキルの実行中に限り適用する**。ユーザーが `/pr-review <N>` を実行した時点でマージが承認されたものとみなし、
  レビューで問題がなければ AI がマージまで実施してよい。
  ただし「マージ前チェックリスト」（ステップ4）を全て満たすことが条件。1つでも満たさない場合はマージせずユーザーに報告する。

## 手順

### ステップ1: PR 情報と差分の取得

```bash
gh pr view <N>
gh pr diff <N>
```

PR のタイトル・本文・ブランチ名・変更ファイル一覧を確認する。

### ステップ2: 変更ファイルの詳細読み込み

差分から変更ファイルを特定し、必要に応じて関連ファイル（呼び出し元・呼び出し先）も合わせて読み込む。

### ステップ3: レビューチェック

以下の観点でコードを確認する。

**バグ・ロジックエラー**
- null 安全が守られているか（null チェック漏れ、`!` 強制アンラップの乱用）
- 非同期処理のエラーハンドリングが適切か
- リスト・マップへのアクセスで IndexOutOfRange / KeyNotFound が起きうる箇所はないか
- 状態変数の更新漏れ・二重更新・競合がないか
- **日付・時刻**: `DateTime.now()` をフィールド初期化子で1度だけ評価していないか。
  アプリを起動したまま日付を跨いだ場合に「今日」がズレないか（resume時の再同期があるか）

**CLAUDE.md 規約適合**
- 依存方向が screens→providers→services→models になっているか
- コメントが日本語で書かれているか
- コミットメッセージが Conventional Commits 形式か
- **エラーをサイレントに無視していないか**（空の catch ブロック、握り潰し）

**セキュリティ**
- APIトークン・パスワードが git 管理ファイルに含まれていないか
- ユーザー入力が適切にバリデーションされているか
- ユーザー向けエラー文言に例外オブジェクト（`$e`）をそのまま埋め込んでいないか

**データ整合性**
- DB マイグレーションが累積方式になっているか
- `toMap`/`fromMap` でフィールドの取りこぼしがないか
- **新しいテーブル・永続データを追加した場合、`export_service.dart` のエクスポート/インポート両方に反映されているか**
  （バックアップ漏れはサイレントなデータ消失につながる）

**パーミッション**
- 新しい OS パーミッションが必要な機能を追加した場合、実行時に要求する導線があるか
  （マニフェスト宣言だけでは Android 13+ で機能しない）

**パフォーマンス**
- 不必要な `setState` / `notifyListeners` の呼び出しがないか
- ループ内で重い処理（DB クエリ・API 呼び出し）を繰り返していないか

### ステップ4: マージ前チェックリスト（必須）

以下を**実際にコマンドを実行して**確認する。結果は報告に含めること。

```bash
# 静的解析（error / warning が1件でもあればマージ不可。info は対象外）
flutter analyze

# テスト（失敗が1件でもあればマージ不可）
flutter test

# PR の状態確認（CI・コンフリクト・レビュー状態）
gh pr view <N> --json mergeable,mergeStateStatus,statusCheckRollup,reviewDecision
```

| # | 条件 | 満たさない場合 |
|---|---|---|
| 1 | `flutter analyze` に error / warning が無い（info は除く） | マージ不可 |
| 2 | `flutter test` が全て成功 | マージ不可 |
| 3 | `mergeable` が `CONFLICTING` でない | マージ不可（rebase を案内） |
| 4 | CI（statusCheckRollup）に失敗が無い | マージ不可 |
| 5 | ステップ3で 🔴 必須修正が0件 | マージ不可（変更依頼へ） |

**1つでも満たさない場合はマージせず、理由をユーザーに報告して指示を仰ぐ。**

### ステップ5: 判定

**全チェック通過 → マージ**

```bash
gh pr merge <N> --merge --subject "<PRタイトル>" --delete-branch
```

マージ後にユーザーへ報告する:
```
PR #<N> をマージしました。
- flutter analyze: error / warning なし
- flutter test: 全<N>件成功
- CI: 成功 / コンフリクト: なし
ブランチ feat/xxx は削除されました。
```

マージ後、PR が Issue を close する場合は、Issue が実際に閉じたかを確認して報告する。

**問題あり → 変更依頼**

```bash
gh pr review <N> --request-changes --body "<指摘内容>"
```

指摘内容の形式:
```
## レビュー指摘事項

### 🔴 必須修正
- [ファイル名:行番号] 問題の説明と修正方針

### 🟡 推奨修正
- [ファイル名:行番号] 問題の説明と修正方針
```

変更依頼後、ユーザーに指摘事項を伝え、修正後に `/pr-review <N>` を再実行するよう案内する。

## 注意事項

- マージ方法はデフォルト `--merge`（スカッシュが必要な場合は `--squash`）
- 既存コードと同等レベルの `info` 警告は指摘対象としない（新規の `warning`/`error` のみ対象）
- セキュリティ上の問題（トークン漏洩など）は必ず🔴とする
- 🟡 推奨修正のみの場合はマージしてよいが、指摘内容は報告に残す
- レビュー対象は PR の差分に限る。差分外の既存の問題を見つけた場合は、マージを止めず別Issueとして起票を提案する
