実装した機能のUI/UX・文言をアプリ利用者視点でレビューし、違和感を報告する。

## 前提

- 引数（$ARGUMENTS）にIssue番号を指定する。例: `/ux-review 68`
- `.claude/designs/issue-<N>.md` が存在すること
- 現在のブランチが対象 Issue の実装ブランチであることが望ましい

## レビューの視点

「このアプリを初めて使う日本人スマートフォンユーザー」の立場でレビューする。
技術的な正しさではなく、**使いやすさ・分かりやすさ・自然な日本語**を評価する。

## 手順

### ステップ1: 設計書と変更ファイルの読み込み

1. `.claude/designs/issue-<N>.md` を読み込み、実装した機能とUI設計を把握する
2. `git diff main...HEAD --name-only` で変更ファイル一覧を取得する
3. `lib/screens/` 以下の変更・新規作成ファイルをすべて読み込む
4. 関連する `lib/widgets/` があれば合わせて読み込む

### ステップ2: 文言レビュー

以下の観点で、画面内のすべてのテキストを確認する:

**ラベル・ボタン文言**
- 操作を正確に表しているか（「保存」「登録」「記録」の使い分けなど）
- 短すぎて意図が伝わらない、または長すぎて読みにくくないか
- 「する」「します」「してください」などの語尾が画面内で統一されているか
- カタカナ外来語の表記が他画面と統一されているか（例: センサー vs. Sensor）

**メッセージ・説明文**
- エラーメッセージは原因と対処法が分かるか
- 空状態のメッセージは次のアクションに繋がるか
- SnackBar の文言は何が起きたか明確か
- ダイアログの「確認」ボタンや「削除」ボタンは誤操作を防ぐ文言か

**プレースホルダー・ヒント**
- 入力欄のプレースホルダーは具体的で役立つか
- 単位（℃、%、日など）は適切な位置にあるか

### ステップ3: 操作フロー・遷移レビュー

**タスク完了までの手順数**
- 目的の操作に到達するまでのタップ数は適切か
- 設定が必要な場合の案内は分かりやすいか（設定画面へのリンクなど）

**フィードバック**
- 操作後に結果が明確に分かるか（成功・失敗のフィードバックがあるか）
- ローディング中は何をしているか示されているか
- 非同期処理中に二重タップを防ぐ制御があるか

**ナビゲーション**
- 「戻る」ボタンでどこに戻るか直感的に分かるか
- 画面タイトルは現在地を示しているか
- タブ名は内容を正確に表しているか

### ステップ4: 視覚・レイアウトレビュー（コードから読み取れる範囲）

**情報の優先順位**
- 最も重要な情報が最初に目に入るレイアウトか
- 「--」などのプレースホルダー表示はユーザーに意図が伝わるか

**空状態・エラー状態**
- データがない場合に何もない画面になっていないか
- エラー時に適切なフィードバックがあるか

**一貫性**
- 他の画面と同じパターンのUI要素を使っているか
- 削除操作は他画面と同じUX（確認ダイアログ、長押しなど）か

### ステップ5: レビュー結果の報告

以下の形式で報告する:

```
## UI/UXレビュー結果（Issue #<N>: <タイトル>）

### 🔴 要修正
修正しないと使いにくい、または意味が通じない問題。

- [ファイル名:行番号] 問題の説明
  - 現在: 「xxx」
  - 提案: 「yyy」
  - 理由: ...

### 🟡 改善推奨
修正した方がより良いが、必須ではない問題。

- [ファイル名:行番号] 問題の説明
  ...

### 🟢 確認事項
コードから読み取れないため、実機で確認が必要な項目。

- [ ] ...

### ✅ 良い点
意図的に評価すべきUX上の工夫。

- ...
```

### ステップ6: 修正の実施

🔴（要修正）の項目について、修正するかユーザーに確認する。
「修正する」と言われた場合はその場で修正してコミットする。
修正コミットのメッセージ:
```
ux: <変更概要> (#<N>)
```
