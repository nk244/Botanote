実装した機能の静的解析・テスト実行・手動確認観点をレポートする。

## 前提

- 引数（$ARGUMENTS）にIssue番号を指定する。例: `/test 156`
- `.claude/designs/issue-<N>.md` が存在すること。なければ「設計書が見つかりません」と案内して停止する
- 現在のブランチが対象 Issue の実装ブランチであることが望ましい（`git branch --show-current` で確認）

## 手順

### ステップ1: 設計書の確認

`.claude/designs/issue-<N>.md` を読み込み、「テスト観点」セクションを取得する。

### ステップ2: 静的解析

```bash
flutter analyze
```

結果を記録する（エラー件数・警告件数）。

### ステップ3: テスト実行

```bash
flutter test
```

テスト結果を記録する（総件数・成功件数・失敗件数）。
失敗したテストがある場合は、テスト名とエラーメッセージを列挙する。

### ステップ4: 差分の確認

```bash
git diff main...HEAD --stat
```

変更ファイルの一覧を確認し、設計書の「変更対象ファイル」と照合して
設計から大きく逸脱していないかチェックする。

### ステップ5: テスト結果レポートの提示

以下の形式でサマリーを提示する:

```
## テスト結果サマリー（Issue #<N>: <タイトル>）

### 静的解析（flutter analyze）
- 結果: エラーなし ✅ / エラーあり ❌（N件）
- 警告: N件

### 自動テスト（flutter test）
- 結果: 全テスト成功 ✅ / 失敗あり ❌
- テスト総数: N件
- 失敗したテスト:
  - <テスト名>: <エラーメッセージ>

### 手動確認チェックリスト
設計書の「テスト観点」から転記:
- [ ] <確認項目1>
- [ ] <確認項目2>
...
```

### ステップ6: 問題への対応

**静的解析エラーがある場合**
エラー内容を提示し、修正するか確認を求める。
修正する場合はそのまま対応し、完了後に再度 `flutter analyze` を実行する。

**テスト失敗がある場合**
失敗の原因を調査し、実装バグか既存テストとの不整合かを判断して報告する。

**すべて問題なし**
「自動確認は完了です。手動チェックリストをもとに実機で動作を確認してください」と案内する。
