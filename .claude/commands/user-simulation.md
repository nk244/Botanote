様々な立場のペルソナになりきり、初インストールから数日〜数年分のアプリ利用をシミュレーションして不具合・違和感を発掘する。

## 前提

- 引数（$ARGUMENTS）は任意。例:
  - `/user-simulation` → ペルソナ・日数ともにランダム決定（通常モード）
  - `/user-simulation ベテラン主婦` → ペルソナを指定、日数はランダム（通常モード）
  - `/user-simulation 5日` → 日数を指定、ペルソナはランダム（通常モード）
  - `/user-simulation フルモード` / `/user-simulation MAX` / `/user-simulation 数年分` → **拡張モード**（下記参照）
  - `/user-simulation IoT好きエンジニア フルモード` → ペルソナ指定＋拡張モード
- Androidエミュレーター（`Medium_Phone_API_36.1`）を使用する
- `ux-review` と同様に uiautomator 経由でUI要素を操作する（座標のハードコーディングを避ける）
- **不具合の修正は行わない**。あくまで利用シミュレーションと発見・報告が目的（修正は `/ux-review` や通常の実装フローに委ねる）

## モードの選択

### 通常モード（デフォルト）
3〜7日（引数指定があればその日数）を、実際に1日ずつ丁寧に操作してシミュレーションする。

### 拡張モード（フルモード）
引数に「フル」「MAX」「長期」「年」「数年分」などのキーワードが含まれる場合に起動する。
**日数の上限を設けず、使用可能なトークン予算のギリギリまでシミュレーションを継続する。** 目安として数週間〜数年分のアプリ利用を模擬し、長期運用でしか顕在化しない問題（DBの肥大化、日付跨ぎ処理、通知の蓄積、バックアップの世代管理、植物の入れ替わりなど）を発掘することが目的。

拡張モードの詳細な進め方はステップ4〜6に記載する。**モードが不明瞭な場合は通常モードを既定とする。**

## ステップ1: ペルソナの決定

引数で指定がなければ、以下の候補からランダムに1つ選ぶ（サイコロを振るように無作為に選定し、選定理由は書かない）。

| # | ペルソナ | 属性 | 植物経験・所有数 | 利用スタイル |
|---|---|---|---|---|
| 1 | 一人暮らしの新米社会人 | 26歳・観葉植物初心者 | 観葉植物1鉢を最近購入したばかり | アプリの使い方に不慣れ。通知だけが頼りで、気づくと数日放置しがち |
| 2 | 多肉・サボテンマニアの大学生 | 20歳・収集歴3年 | 10鉢以上所有、日々増える | こまめに写真を撮ってノートに記録。タグ機能を細かく使い分けたい |
| 3 | ガーデニング歴20年のベテラン主婦 | 52歳・几帳面 | 庭木〜鉢植えまで15鉢 | 水やり・肥料・活力剤の間隔を細かくカスタマイズ。定期的にバックアップを取る |
| 4 | IoT・ガジェット好きの会社員エンジニア | 34歳・中級者 | 観葉植物5鉢、Nature Remo/SwitchBot所有 | センサー連携・環境ダッシュボードを真っ先に試す。テーマやダークモードにもこだわる |
| 5 | 忙しい共働きの親 | 40歳・子どもと家庭菜園中 | ミニトマト・ハーブなど3鉢 | 平日はほぼ開かず週末にまとめて記録。通知を見逃しがち、一括記録機能に頼る |
| 6 | 水やりを忘れがちな新米ズボラ | 29歳・ズボラ | 観葉植物2鉢、過去に1鉢枯らした経験あり | 通知設定を試行錯誤。誤って記録してしまい取り消し機能を多用する |

**通常モード**: 日数は指定がなければ3〜7日の範囲でランダムに決定する。
**拡張モード**: 固定の日数は決めない（ステップ4〜6の終了条件に従って自然に終わる）。

決定したペルソナとモード（＋通常モードなら日数）をユーザーに一言で報告してからシミュレーションを開始する。
（例:「今回は『IoT・ガジェット好きの会社員エンジニア（34歳）』として拡張モード（数年分）で利用します」）

## ステップ2: シナリオの立案

選んだペルソナの性格・目的に基づき、時間単位で「その時期にやること」を具体的に計画する。
以下の機能一覧から、ペルソナに合うものを割り振る（全部を1日に詰め込まない。数日サボる・後回しにするなどの「人間らしい行動のムラ」も再現する）。

**カバーすべき機能領域**（`lib/screens/` 対応）
- オンボーディング・初回起動（`home_screen.dart`）
- 植物の登録・編集・画像設定/トリミング（`add_plant_screen.dart`, `image_crop_screen.dart`）
- 植物一覧のリスト/グリッド切り替え・並び替え（`plant_list_screen.dart`）
- 植物詳細の閲覧（`plant_detail_screen.dart`）
- 水やり・肥料・活力剤・植え替え・剪定・葉水・掃除ログの記録（`today_watering_screen.dart`、`LogType` 全種）
- 日付を跨いだログ確認・カレンダービューでの日付選択
- 一括記録・一括取り消し
- ノートの作成・編集・タグ付け・画像添付・検索（`notes_list_screen.dart`, `add_edit_note_screen.dart`, `note_detail_screen.dart`）
- 置き場所（ロケーション）の作成・植物やセンサーとの紐付け（`location_list_screen.dart`, `location_detail_screen.dart`）
- IoTセンサー連携設定（Nature Remo / SwitchBot）とセンサーログ確認（`iot_settings_screen.dart`, `sensor_log_screen.dart`）
- 照度計測（`light_meter_screen.dart`）
- ケア統計・成長タイムライン（`care_stats_screen.dart`, `plant_growth_timeline_screen.dart`）
- 通知設定（時刻変更・ON/OFF）とリマインダー受信確認
- テーマ設定（カラー4種・ライト/ダーク/システム）
- ZIPバックアップ・エクスポート・インポート（`settings_screen.dart`）

**通常モードのDay割り当ての目安**
- Day1: 初インストール、オンボーディング、最初の植物登録、初回のログ記録
- 中盤: ペルソナの本性が出るところ（几帳面なら間隔設定を細かく調整、ズボラなら通知を試行錯誤、IoT好きならセンサー連携を試す等）
- 終盤: バックアップ/エクスポート、統計・タイムラインの確認、忙しいペルソナなら「数日ぶりに開いて一括記録」などのシナリオ

**拡張モードの時間軸の目安**（詳細な密度設計はステップ4参照）
- 初週: 通常モードと同様に毎日詳細に操作
- 1〜3ヶ月目: 植物が増える・ノートが積み上がる・間隔設定を見直すなどの「定着期」
- 半年〜1年目: 季節変化（水やり頻度の見直し、休眠期対応）、バックアップからの復元テスト
- 2年目以降: 植物の入れ替わり（枯死・処分・新規購入）、機種変更を想定したバックアップ→アンインストール→再インストール→復元、蓄積ログでの一覧・統計表示のパフォーマンス確認

立案したプランを短くユーザーに提示してから実行に移る。拡張モードの場合はマイルストーン（1ヶ月目、半年目、1年目、…）単位で構わない。

## ステップ3: 環境準備（初インストール状態を作る）

```bash
# エミュレーター起動確認
adb devices
flutter emulators --launch Medium_Phone_API_36.1
adb wait-for-device shell getprop sys.boot_completed

# 既存インストールがあれば完全に削除（データ・通知含めてまっさらにする）
adb uninstall com.example.bota_note

# デバッグビルドをインストール
flutter build apk --debug
adb install build\app\outputs\flutter-apk\app-debug.apk
```

スクリーンショット・進捗ログの保存先を作成する:
```
C:\Users\zorn5\AppData\Local\Temp\claude\C--Users-zorn5-source-botanote\sim_screenshots\<ペルソナ名>\day<N>\
C:\Users\zorn5\AppData\Local\Temp\claude\C--Users-zorn5-source-botanote\sim_screenshots\<ペルソナ名>\progress_log.md
```

`progress_log.md` は拡張モードで特に重要（ステップ5参照）。作成したら空のMarkdownファイルとして初期化しておく。

## ステップ4: 操作の基本手順（共通）

`ux-review` と同じ手法を使う。

```bash
# アプリ起動
adb shell am start -n com.example.bota_note/.MainActivity

# UI要素の座標取得
adb shell uiautomator dump /sdcard/ui.xml
adb pull /sdcard/ui.xml "C:\Users\zorn5\AppData\Local\Temp\claude\...\ui.xml"

# タップ・入力・スクロール・戻る
adb shell input tap <X> <Y>
adb shell input text "サンプルテキスト"
adb shell input keyevent 4
adb shell input swipe 540 1400 540 700 500

# スクリーンショット
adb exec-out screencap -p > ".../day<N>_<画面名>.png"
```

各操作の後、想定通りの挙動になっているかをスクリーンショットとuiautomator dumpの両方で確認する。
異常（クラッシュ・フリーズ・ANR・意図しない画面遷移）が起きた場合は `adb logcat -d | tail -n 200` で直前のログを確認し、記録しておく。

日付を進めて複数日利用を再現する手順:

```bash
# 自動時刻同期をオフにする（初回のみ）
adb shell settings put global auto_time 0

# root権限で日時を進める（例: 2026-07-14 09:00:00 に設定）
adb root
adb shell "date -s '2026-07-14 09:00:00'"
# 失敗する（root化できない/読み取り専用システムイメージ等）場合は、
# 「設定 > システム > 日付と時刻」画面をuiautomator経由で操作し、手動設定に切り替えて日時を進める
```

日付を進めたら、通知（水やりリマインダー等）が正しいタイミングで届くか確認する:
```bash
adb shell dumpsys notification --noredact | grep -A 5 "com.example.bota_note"
```

> ⚠️ **重要**: シミュレーション終了後は必ず日時を実際の日時に戻し、`auto_time` を `1` に戻すこと（ステップ7で必須実施）。

## ステップ5: 拡張モードの進め方（トークン予算のギリギリまで継続する）

拡張モードは「毎日UIを丁寧に操作する」を何年分も繰り返すとトークンを浪費して現実的でないため、**時間経過とともに操作密度を疎にするサンプリング戦略**を取る。

### サンプリング密度

| 経過期間 | 詳細操作の頻度 | 内容 |
|---|---|---|
| 1週目 | 毎日 | 通常モードと同じ粒度でUI操作・スクショ・所感を記録 |
| 2〜4週目 | 2〜3日に1回 | 主要機能を一巡（ログ記録・ノート・統計確認） |
| 2〜6ヶ月目 | 週1回 | 定期メンテ的な操作（バックアップ、間隔設定の見直し等） |
| 半年〜2年目 | 月1回 | 季節イベント（休眠期対応、植物の入れ替え、機種変更＝アンインストール→復元テスト等）を挟む |
| 2年目以降 | 3ヶ月に1回 | 蓄積データでの一覧表示・統計・カレンダーのパフォーマンスや不具合の有無を重点確認 |

サンプリングの間（詳細操作をしない期間）は、UIを逐一操作せず `adb shell date -s ...` で日付だけを飛ばして進める。詳細操作のタイミングでは必ずアプリを起動し直し、スクリーンショットを撮って画面が壊れていないか確認する。

### 終了条件（いずれかを満たしたら打ち切り、ステップ7へ進む）

- コンテキストが自動要約されそうな量に近づいてきたと判断したとき（会話が長くなってきた、大量のスクショ・ログを読み込んだ等の兆候）
- 計画したマイルストーン（例:「5年分」）に到達したとき
- 重大な不具合を発見し、それ以上進めるより先に報告すべきと判断したとき
- ユーザーから停止の指示があったとき

**「まだ余裕がありそうならもう少し進める」を基本姿勢とする**（早期に切り上げすぎない）。ただし各詳細操作のたびに `progress_log.md` へ追記し、いつ打ち切っても報告を組み立てられる状態を保つ。

### 進捗の永続化（コンテキスト圧縮対策）

拡張モードは長時間・大量のやり取りになり会話が要約される可能性があるため、詳細操作を行うたびに `progress_log.md` に以下を追記する（会話内の記憶だけに頼らない）。

```markdown
## <経過期間ラベル>（シミュレーション内日付: YYYY-MM-DD）
- 実施した操作: ...
- 所感（ペルソナ視点）: 「...」
- 気になった点: ...
- スクリーンショット: day<N>/xxx.png
```

打ち切り時・最終報告作成時は、会話の記憶ではなく **この `progress_log.md` を読み直して** レポートを組み立てる。

## ステップ6: ペルソナとして行動する

各詳細操作のタイミングで、ステップ2で立てたプランに沿って実際に操作する。操作しながら、ペルソナの一人称視点で「思ったこと」を書き留める（UXレビューの材料になる）。

例:
- 几帳面なペルソナ:「間隔設定が『N日ごと』と『N回に1回』のどちらか選べて助かる。でも設定画面から一度離れると保存されているか不安になる」
- ズボラなペルソナ:「通知が来たのに植物選択画面まで2タップかかるのが地味に面倒。もっと通知から直接記録したい」
- IoT好きペルソナ:「Nature RemoのAPIキーを持っていないので連携エラーになったが、エラーメッセージだけで原因が分かるか確認したい」
- 拡張モードで数年目のペルソナ:「植物が増えすぎて一覧が探しにくくなってきた」「昔登録した植物を削除したらノートやログはどうなるのか気になる」

IoTセンサー連携など実際の外部APIキーが必要な機能は、実際には接続できないため「未設定時のエラーハンドリング・案内文言が適切か」を確認する観点で操作する（実際のNature Remo/SwitchBot APIとの疎通は対象外）。

拡張モードでは「機種変更」を模したシナリオも有効: ZIPバックアップを作成 → `adb uninstall` → 再インストール → バックアップから復元、という一連の流れで長期利用者が経験しうる操作を検証する。

## ステップ7: 後片付け

シミュレーション終了後、必ず実施する:

```bash
# 日時を実際の現在時刻に戻す
adb shell settings put global auto_time 1
adb shell "date -s '$(powershell -NoProfile -Command "Get-Date -Format 'yyyy-MM-dd HH:mm:ss'")'"

# 動作確認（現在時刻に戻っているか）
adb shell date
```

アプリ自体はアンインストールせず残しておいてよい（次回のシミュレーションや実機確認の妨げにならない限り）。
